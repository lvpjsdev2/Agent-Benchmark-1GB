# Методика сравнения агентов

## 0. Правило воспроизводимости

Перед каждой серией сохранять: дату UTC, регион Oracle (без адресов/ID), образ ОС и ядро, версию Docker/Podman (если используется), параметры CPU и RAM, swap, количество доступной памяти, фоновые процессы, бинарник/образ с версией и digest/commit, config без секретов, LLM endpoint и модель, длительность, ограничения ресурсов.

Не сопоставлять нативный процесс одного агента с Docker-окружением другого в одной колонке без пометки. Основной результат — **полный жизненный цикл**, включая зависимые процессы и контейнеры; дополнительные результаты — только основной процесс.

## 1. Двухступенчатый стенд

**Проверка на Mac:** исходники и происхождение релизов, установка, подготовка конфигурации, простой диалог и поддержка инструментов. Mac не является источником Linux-метрик.

**Сравнение на Oracle:** запуск строго одного кандидата за раз на одной и той же конфигурации Linux. При существенном влиянии соседних приложений результаты признаются непригодными для прямого сравнения; предпочтительна чистая отдельная VM в квоте Free Tier. Создавать новую VM без проверки лимитов и согласования нельзя.

## 2. Режимы запуска

- **Native**: официальный предварительно собранный бинарник, если разработчики выпускают подходящий Linux x86-64 артефакт, с проверкой SHA/подписи при наличии.
- **Docker**: официальный образ, закреплённый digest, одинаковые ограничения, без привилегированного режима.
- Если нативного варианта нет, Docker-запуск разрешён, но это помечается в сравнении. Ресурсные показатели разделяются по режимам запуска.
- Не компилировать тяжёлые Rust/Go-зависимости на Micro для чистоты измерений: сборка на другой машине с проверкой архитектуры или официальный релиз.

## 3. Сценарии

### A. Cold start / idle

1. Замер базового состояния VM после 5 минут без тестируемого агента.
2. Старт агента; ожидание доступности (healthcheck/API или функциональный CLI-командный тест).
3. Измерение времени запуска, RAM и CPU: минимум 10 минут с шагом 1 с, первые 60 с отдельно.
4. Минимум 3 повтора с очисткой завершённых процессов. Первую установку и загрузку образа не включать во время старта.

### B. Mock LLM: контролируемые запросы

1. Запустить простой OpenAI-совместимый mock endpoint с предопределёнными ответами. Его ресурсы измерять отдельно; по возможности расположить вне Micro, а фиксированную сетевую задержку контролировать.
2. 30 последовательных идентичных запросов, прогрев 5 запросов вне выборки.
3. Вычислить медиану и p95 end-to-end латентности, RSS/PSS, peak, CPU, ошибки, HTTP timeouts и число токенов при наличии.
4. В отдельном наборе — 10 инструментальных циклов, если агент поддерживает совместимый формат tool calls. Если нет — фиксировать N/A, не считать нулевой нагрузкой.

### C. Реальный LLM и полезные действия

Один провайдер + одна версия модели, одинаковые temperature, max_tokens, system prompt, ключевые инструкции и ограничения. Тестовые задачи:

- Ответить на короткий проверяемый вопрос без инструментов.
- Прочитать созданный тестовый файл и извлечь три заданных значения.
- Создать в разрешённом временном каталоге файл с JSON-сводкой (схему проверить автоматически).
- При наличии MCP: вызвать **локальный безвредный** тестовый MCP-инструмент `echo`/`add`; считать отдельным функциональным тестом.

На каждую задачу 5 повторов; сохранять успех, ошибки, потраченные токены, итоговую RAM/CPU/время. Нестабильность модели фиксировать отдельно, не приписывать её агенту без анализа.

### D. Устойчивость и восстановление

- 100 последовательных mock-запросов с небольшой паузой, проверка утечек и незавершённых процессов.
- Перезапуск процесса; при предусмотренной памяти — проверка сохранения тестового состояния.
- Симуляция ошибок API (429, 500, timeout) и проверка контролируемого повторения/обработки.
- Отдельный суточный тест без браузера/MCP-демонов для 2–3 лучших кандидатов только при наличии изолированного свободного хоста.

## 4. Определения метрик

| Метрика | Как считаем | Комментарий |
|---|---|---|
| RAM baseline | `MemAvailable` до запуска | Нужен резерв ОС |
| Main-process PSS / RSS | `/proc/<pid>/smaps_rollup`, `/proc/<pid>/status` | PSS лучше отражает общие страницы |
| Service RAM peak | сумма по cgroup `memory.peak` либо учёт всех дочерних процессов | Для Docker и зависимых служб |
| Total system memory | `MemAvailable`, `memory.current`, OOM counters | Проверять давление на память |
| CPU | cgroup `cpu.stat`/`docker stats` и `/proc` | Процент относительно квоты CPU, а не «целого ядра» |
| Latency | client wall clock | Медиана, p95, ошибки |
| Startup | процесс запущен → успешный health/ответ | Не включать скачивание образа |
| Disk | размер бинарника/образа, рабочей директории, рост БД и логов | Отдельно разовый и постоянный объём |
| Reliability | успешные тесты / все запрошенные тесты | OOM и аварийные завершения отдельно |

Sampling: 1 секунда; для быстрых пиков дополнять cgroup peak. Минимум 3 прогона сценариев A–B; указывать вариацию результатов. При наличии swap фиксировать количество swap-in/swap-out: использование swap может скрывать проблемы RAM и искажать latency.

## 5. Справедливость сравнения

- Одни и те же тестовые файлы, API-контракт, промпты и ограничение вывода.
- Поддержку функций проверять отдельно от resource-cost: отсутствующая функция — `unsupported`, а не «0 MB».
- Если приложение создаёт дополнительные процессы (MCP, shell, браузер), учитывать полный расход ресурсов.
- Мониторинг не должен заметно влиять на результаты; отделить результаты самого monitor-процесса.
- Логи и кэш ограничить; одинаковые правила очистки между прогонами; явно отмечать тесты холодного и тёплого запуска.
- Измерения прерывать при давлении на память, OOM, существенных проблемах соседних сервисов или превышении API-бюджета.

## 6. Скоринг (после функциональных «ворот»)

Предлагаемые веса: RAM+CPU 30%; стабильность 25%; функциональность 20%; безопасность 15%; удобство поддержки 10%. Каждая оценка 0–5 с описанным основанием и исходными метриками. Это предварительная система оценок; менять веса после просмотра победителя нельзя, только до испытаний.

Непрошедшие обязательные требования (запуск, безопасная конфигурация, базовый диалог, отсутствие системных OOM) маркируются **неподходящими для целевой VM**, даже при высоком функциональном балле.

## 7. Формат исходных данных

Каждый прогон сохраняет `run_id`, `agent`, `repo_url`, `version`, `mode`, `scenario`, `host_profile`, `started_at_utc`, `duration_sec`, `ram_pss_mb_median`, `ram_peak_mb`, `cpu_sec`, `startup_ms`, `latency_p50_ms`, `latency_p95_ms`, `success_count`, `error_count`, `oom_count`, `notes`, ссылки на конфигурацию и обезличенные логи.

Нельзя помещать в результаты API-ключи, Telegram-токены, токены авторизации, IP-адреса и личные сообщения.
